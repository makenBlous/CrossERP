## 1. 项目定位

CrossERP 是面向中国境内主体、做出口跨境电商的智能体 ERP：把平台结算和业务文件导入系统，用确定性代码完成清洗、对账、利润、异常处理和凭证流程，并以权限、审批和审计保护写入。智能体（DeerFlow 以 SDK 嵌入、独立 worker）按登录人权限办事，不能执行代码，也不能计算金额。

当前是对外展示用的演示产品，不是真实上线环境。会计、税务相关配置使用演示默认值，并注明「真实使用前需核实」。会计按中国准则、人民币（CNY）本位币；出口退税等税务口径见 07，确认前不展开真实申报。

实施按 P0–P5 分批，不把后期模块提前当成已交付功能。

## 2. 技术栈与目录结构

- 后端：Python 3.12+、uv、FastAPI、SQLAlchemy 2、Alembic、Pydantic 2、Typer；包名 `src/crosserp`，CLI `crosserp`，环境变量 `CROSSERP_` 前缀。
- 数据库：正式环境 MySQL 8.4；本机演示和默认测试用 SQLite（默认路径 `~/.crosserp/data.db`，测试不得使用）；PostgreSQL 仅在明确满足替换条件时采用。金额 `Money = {amountMinor: int, currency}`，万分位整数（SCALE = 10000），禁止浮点。
- 前端：`frontend/` 为 Vue 3 + TypeScript + Vuetify 3 + Vite，复用本机 Vuexy 参考的静态原型；API 仍是 mock，不能称为已接后端。历史 Jinja 网页仍在 `src/crosserp/web`。
- 目标接口：Vue 前端所需 `/api/v1` JSON 以 08 v4、实体目录和 OpenAPI 草案为准，不要从页面 mock 反推。

仓库根目录（`D:\make\write\work\CrossERP`）主要包含：`src/crosserp/`（后端，含 `api`、`platform`、`iam`、`catalog`、`connectors`、`recon`、`profit`、`ledger`、`approval`、`audit`、`agent` 等）、`tests/`、`frontend/`、`docs/`（`design/`、`tasks/`、`backend/`、`dev/`、`domains/`、`adr/`）、`scripts/`、`config/`、`deploy/`、`AGENTS.md`。功能工作树在仓库外的 `D:\make\write\work\CrossERP-wt\<树名>`，不是仓库内目录。

## 4. 已定产品与架构决策

每条日期是 maken 拍板或写入设计的日期，不是代码合入日期。完整表述以 07、08 第 12 章为准。

### 4.1 2026-11-10（07：演示默认值）

- 07 按对外演示确定原待拍板项；会计相关项真实使用前需会计核实，改动只改配置或 `accounts.yaml`。
- 本位币 CNY；v1.0 单法人多店铺，预留可空 `company_id`；数量用整数件。
- 成本默认移动加权平均；税只做到计提和开票数据，不做申报代办；出口退税以跟踪表为后期能力，退税率等确认前不展开计算。

### 4.2 2026-11-11（08 v3 第一次回复，v4 第二次回复）

- 沿用现有 Python 后端；正式库以 MySQL 为主；内网、一个法人，不做多租户。
- 以本体实体为核心，接口是实体动作的投影；写动作走统一 ActionDispatcher。
- DeerFlow 只用 SDK、不单独部署；agent 跑在独立 worker 和独立 Python 环境；通行证全自动、用户无感，登出、切换账号、权限变化、停用或关闭 AI 时立即作废。
- agent 继承登录人权限，只能收窄；子智能体与主智能体执行权相同，每步按被代表人当前权限回查。
- 风险只按是否改数据分级：只读（含钱和账的查询）AI 可直接做；低/中风险 AI 可直接做，中风险不设次数限额，必须 24 小时内可撤销，只进每日一条站内摘要；高风险（改账类）AI 最多到起草/待审；critical（权限、审批决定等）AI 禁用，仅真人。
- 审批人从流程配置解析：配了就必须审（法人/老大也一样），不能自批；没配或解析不到可用账号时，人发起的直接生效并留痕；AI 发起的高风险或钱账动作退回发起人本人确认。不设金额上限；单人模式取消。
- 模型兼容 OpenAI 接口，前端填写 `baseUrl`、`apiKey`、`model`；密钥加密存储、不回显、不进日志。
- **禁止 AI 执行代码**：不开 bash、不开沙箱、不装 Docker。关闭 AI 后人工流程必须可用。金额由确定性代码计算，AI 只解释、建议和引用。
- 平台接入顺序：文件导入 → Amazon SP-API → Shopify → 领星。外部账套先金蝶、再用友、其次其他。审批先在平台内，IM 后期；渠道用可插拔适配器。
- 人事、行政、CRM、广告放在 P5。定时任务由 CrossERP 自己调度。

## 5. 开发规则摘要

细节只维护在 [rules.md](tasks/rules.md)，此处是方便同步的摘要。

- 开发工具：新任务用 grok CLI（自动批准、不开子 agent）；一功能一 agent、一个 detached 工作树、独立测试库和分配的端口。
- 禁止防御性编程（t155u）：不写 `.get` 默认值、`or {}`、吞异常、静默 `return`、假成功、兼容开关；错误显式抛出。安全边界（权限、范围、审批、审计、幂等、撤销、AI 风险档、密钥）必须严格实现，不算防御性代码。
- 不得为过关删除或放宽安全相关测试断言；偶发失败只能原样重跑，连续两次失败按真问题处理。修正用新提交，不 amend、不 rebase、不 `reset --hard`、不改已当作基线的提交。
- 合并前：`scripts/check_merge_guard.py` 自动检查，再由独立只读 grok 按 [acceptance.md](tasks/acceptance.md) 验收；不通过不能合。合入后更新本文。
- 不推送，除非 maken 明确授权；不打 tag、不 force push、不重写历史。全量回归和密钥扫描通过后才能谈推送。
- 任何测试、迁移、脚本都不得读写或改名 `~/.crosserp/`。`data.db` 重建只在指定的合并步骤做，旧库只改名备份，不删除。
- 不读 `CrossERP演示密码.txt`、`.env`、任何密钥或令牌文件。
- 禁用端口 5173、8000、4173（maken 预览）、4184；只用分配的端口。
- 拆工作树：先 `cmd /c rmdir` 删除 `frontend\node_modules` 联接，再 `git worktree remove`（不加 `--force`）。
- 提交用 `git commit -F`（UTF-8 说明文件）；不提交 `_task/`、`last.txt`。只 add 自己改的文件，不得 stash/reset/checkout 覆盖他人未提交改动。
- 必须复用的共用函数（权限、店铺范围、执行器工厂、接口元数据/幂等、审批、审计、撤销等）见 rules.md 第 3 节，禁止各模块自写一套。

## 8. 更新规则

### 何时更新

出现下列情况之一，必须更新本文：

- 有提交合入 main（含文档或修复）。
- maken 作出新的产品、架构或流程决定。
- 监督方作出自主决策（追加编号）。
- 一个功能开工、完成开发、进入合并或被打回。
- 发现阻塞、放行条件变化，或工作树/门控状态变化。

### 怎么更新

- 只改「当前状态」，并在第 4 节或第 7 节**追加**新决策；不要重写整份历史。
- 每条更新带日期（Asia/Shanghai）和相关提交号。
- 保持精简：过时的「当前状态」直接删掉或改成现在的事实；已被推翻的流程在对应条目注明「已被后续决定取代」，不要并排保留两套现行说法。
- 不要写入密钥、口令、连接串、`.env` 内容或 `~/.crosserp` 里的数据。
- 更新放在合入 main 的同一提交，或紧接着的下一次提交。更新后改页首「最后更新」一行：日期时间 / 更新者 / 提交号。
- 正文建议控制在约 300 行以内。

## 9. 与仓库外进度文件的关系
