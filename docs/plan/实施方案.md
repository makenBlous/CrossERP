## 0. 一句话说明（给 maken）

做一个开源（Apache-2.0）的「跨境电商对账 + SKU 利润 + 审批记账」小工具：卖家把 Amazon 结算报告、Shopify 打款明细、领星/赛狐导出表拖进来，系统**用确定性代码**算对账和利润、列出对不上的单子和原因；AI 只负责「解释」和「回答问题并给出处」（历史表述；**已被 08 v4 第 4.4 节取代：只读动作可直接执行，中风险可执行且可撤销，改账最多起草/待审，高危禁用**）；任何写账（导出金蝶凭证、推送 ERPNext）都必须**人在网页上点批准**之后才会发生。整体是 **B/S 架构**：程序跑在一台电脑或服务器上，大家用浏览器登录使用。数据库可选 SQLite（试用）/ MySQL / PostgreSQL（历史表述；**已被 08 v4 第 11.3 节取代：正式环境以 MySQL 8.4 LTS 为主，SQLite 仅演示，PostgreSQL 仅备选**）。每次改数、批准、登录都有不能改的审计记录；每次 AI 调用都记录模型、token、费用和耗时。架构按插件设计，以后能接淘宝/抖店/ERPNext/Odoo，逐步扩成中小企业 ERP。

人话：用户只用浏览器，所有东西都跑在一台服务器上（B/S，见 2.4）。数据从左边进来，先被「连接器」翻译成统一格式存进数据库；对账和利润都是普通代码算的，不靠 AI；要写账的东西先进「审批」，只有批准过的才会从唯一的「写账出口」出去；AI 只能**读**数据库（专用只读账号）（历史表述；**已被 08 v4 第 4.4、10.4 节取代：Agent 可执行与登录人相同的动作，但每步按权限与风险重算，改账仍只能起草/待审**），回答问题时必须给出处；每次 AI 调用进「LLM 监控」，每次改数/批准/登录进「审计」。

### 2.3 连接器插件接口（以后接淘宝/抖店/ERPNext/Odoo 用这个）

```python
# src/agent_erp/connectors/base.py
from typing import Protocol, Iterator, Literal, runtime_checkable
from pathlib import Path
from agent_erp.core.models import RawRow, CanonicalRecord, ColumnMapping, SyncWindow, Credentials

SourceKind = Literal["settlement", "payout", "orders", "costs", "fees", "ads"]

@runtime_checkable
class FileConnector(Protocol):
    id: str                      # "amazon.settlement_v2"、"shopify.payouts"、"lingxing.orders_export"
    kind: SourceKind
    version: str                 # 连接器自身版本，写入每条记录的 provenance
    def sniff(self, path: Path) -> float: ...            # 0~1 置信度，用于自动识别文件类型
    def read(self, path: Path, mapping: ColumnMapping | None) -> Iterator[RawRow]: ...  # 保留原始行号
    def normalize(self, row: RawRow) -> list[CanonicalRecord]: ...                       # 纯函数，可测试

@runtime_checkable
class ApiConnector(Protocol):
    id: str
    kind: SourceKind
    def pull(self, window: SyncWindow, creds: Credentials) -> Iterator[RawRow]: ...     # 只读拉取

# 目标（写账）插件：只能被 ledger.write_service 调用
class LedgerTarget(Protocol):
    id: str                      # "kingdee.cloud_xk_xlsx"、"generic.xlsx"、"erpnext.journal_entry"
    def render(self, batch: "VoucherBatch") -> "Artifact": ...       # 生成文件，不产生外部副作用
    def push(self, batch: "VoucherBatch", approval: "ApprovalToken") -> "PushResult": ...  # 外部副作用
```

- 注册方式：`pyproject.toml` 的 `[project.entry-points."agent_erp.connectors"]`，第三方包（如 `agent-erp-douyin`）装上就能被发现。
- 每条标准记录都带 `provenance = {connector_id, connector_version, import_batch_id, source_file, row_no}`，这是 AI 引用出处的基础。
- 淘宝/抖店/Odoo 在 v1.0 只给接口文档和一个「示例插件模板」，不实现（「推断」：这些平台开放接口需要单独申请，未核实）。
- ERPNext 是 GPL-3.0（GitHub API 查得），我们是 Apache-2.0：**只通过 ERPNext 的 REST 接口对接，不复制它的代码**（「推断」，许可证兼容性建议上线前再确认）。

### 2.4 B/S 架构与多用户角色

**结论：B/S（浏览器 / 服务器）架构，不是 C/S。** 服务器端是一个 Python 程序（FastAPI），数据库和全部计算都在服务器上；用户用浏览器打开网址、登录后使用，不用在每台电脑装客户端。一个人用时，「服务器」就是自己的电脑（只监听 127.0.0.1）；团队用时，把它装在一台办公室电脑或云服务器上，运营、财务、老板、审计员各自用浏览器登录，能看到和能做的事由角色决定。

**为什么不用 C/S（人话）**

| | B/S（本项目） | C/S（不选） |
|---|---|---|
| 用户要装什么 | 只要浏览器 | 每台电脑装一个桌面客户端 |
| 升级 | 服务器升级一次，所有人马上是新版 | 每台电脑都要升级，版本不一致容易出错 |
| 多人审批 | 同一份数据：运营提交，财务在自己电脑上批准 | 需要另做数据同步或让每个客户端直连数据库 |
| 审计 | 所有操作都经过服务器，统一记日志、统一校验权限 | 客户端直连数据库时，很难保证每个动作都被记录（「推断」） |
| 跨系统 | Windows / Mac / Linux 有浏览器就行 | 要给每个系统分别打包 |
| 代价 | 要有一台机器开着；对外开放要配 HTTPS 和登录防护 | 可离线使用 |

**角色与权限（v0.5）**

| 角色 | 能做 | 不能做 |
|---|---|---|
| admin 管理员 | 管用户和角色、系统设置、模型与预算配置、开关「单人模式」（历史表述；**已被 08 v4 第 12.1、12.3 节取代：取消单人模式，无可用审批人时按规则直接生效并留痕**） | 没有 finance 角色时不能批准凭证 |
| finance 财务审批人 | 批准/驳回凭证和映射建议、下载已批准的凭证 | 批准自己提交的单据（单人模式除外，且会被标记）（历史表述；**已被 08 v4 第 4.6、12.1 节取代：不能自批；无可用审批人时按规则直接生效并留痕**） |
| operator 运营 | 导入文件、处理异常、生成凭证草稿、提交审批、AI 问答 | 批准、导出、管理用户 |
| viewer 老板/只读 | 看报表和异常、AI 问答 | 任何修改 |
| auditor 审计员 | 只读业务审计、登录日志、LLM 监控，导出审计包 | 修改任何业务数据 |

- 一个人可以有多个角色；单人使用时 `init` 创建的账号默认拥有全部角色并开启「单人模式」，每次自批在审计中标记 `self_approved`（历史表述；**已被 08 v4 第 12.1、12.3 节取代：取消单人模式**）。
- 部署形态：① 单机试用：`agent-erp serve`，浏览器开 http://127.0.0.1:8000；② 团队：一台服务器 + MySQL 或 PostgreSQL，前面放 HTTPS 反向代理（具体用哪个写进 docs，属「推断」）；③ Docker Compose。【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】
- CLI 和 MCP 服务是同一服务器/数据库的另外两个入口：CLI 在服务器本机执行并记审计；MCP 用 API token 绑定用户和角色，v0.5 只读（历史表述；**已被 08 v4 第 4.4 节取代：Agent 按动作风险分级，不以全局只读限制**）。
- **非目标**：桌面安装包（把服务器和浏览器窗口打包成一个桌面程序）不在 v0.1–v1.0 范围内；以后试用卖家强烈要求时再评估，不改变 B/S 架构（「推断」）。
- 不做：SSO / LDAP、多租户 SaaS、字段级权限（v1.x 以后视需求）。

## 4. 数据模型（关键字段）

金额规则：内存里一律 `decimal.Decimal`；数据库金额列统一是 **`Money4` 类型 = DECIMAL(19,4)**（MySQL `DECIMAL` / PostgreSQL `NUMERIC`，都是精确小数）。SQLite 没有真正的定点小数：NUMERIC 列会把值转成整数或浮点数存（[SQLite 文档](https://www.sqlite.org/datatype3.html)），所以 `Money4` 在 SQLite 上自动存整数「万分位」（1.23 存 12300），业务代码始终只看到 Decimal；超过 4 位小数直接报错。汇率用 DECIMAL(18,8)。只在展示时四舍五入到 2 位（ROUND_HALF_UP）。时间：`UtcDateTime` 存 UTC + 原始时区字符串（MySQL DATETIME 不带时区）。下表中的金额列都是 Money4。【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】

**三库通用规则（写进 AGENTS.md；历史兼容规则，不代表三库并列目标，现行正式目标见 08 v4 第 11.3 节）**
- 只用 SQLAlchemy 通用类型：`String` 必须写长度（MySQL VARCHAR 要求）、`JSON`、`Uuid`、`Boolean`、`Money4`、`UtcDateTime`；禁止 PG 专属 ARRAY / JSONB / 部分索引 / 数据库自定义函数。
- 要建索引的字符串列 ≤ 255 字符：InnoDB 索引前缀上限 3072 字节（DYNAMIC/COMPRESSED 行格式，[文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html)），utf8mb4 每字符最多 4 字节，联合索引要注意总长度。
- MySQL 连接串固定 `?charset=utf8mb4`；建库 `CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`；启动自检：版本 ≥ 8.4、字符集、`sql_mode` 含 `STRICT_TRANS_TABLES`（非严格模式下超长/越界值可能被截断而不报错，金额系统不能接受）。
- upsert、行锁、日期按月分组等方言差异只写在 `db/dialects.py`；业务代码不写原生 SQL。
- 全文检索（`search_rules_doc`）不用数据库自带全文索引，应用内建简单关键词索引，三库行为一致。【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】
- 数据库账号分三个：迁移账号（建表）、应用账号（审计表只 INSERT/SELECT）、智能体账号（只 SELECT）；SQLite 无账号体系，靠 `mode=ro` 连接 + 哈希链。

## 5. 导入规格（每个来源）

### 5.1 Amazon 结算报告（Flat File V2）— 官方文档已核实字段名
- 来源：[Settlement Reports 官方文档](https://developer-docs.amazon/sp-api/docs/report-type-values-settlement)。报告类型 `GET_V2_SETTLEMENT_REPORT_DATA_FLAT_FILE_V2`，制表符分隔（tab-delimited），需要 Finance and Accounting 角色；旧版 Flat File 和 XML 结算报告已弃用。
- 结算报告**不能主动请求或预约**，由亚马逊自动生成，只能用 `getReports` 查找（同一官方文档）。
- 金额按当地格式显示，例如欧洲站是 `95,00` 而不是 `95.00`（官方文档原话）→ 解析器必须按站点区分小数点。
- 字段（官方列表）：`settlement-id, settlement-start-date, settlement-end-date, deposit-date, total-amount, currency, transaction-type, order-id, merchant-order-id, adjustment-id, shipment-id, marketplace-name, amount-type, amount-description, amount, fulfillment-id, posted-date, posted-date-time, order-item-code, merchant-order-item-id, merchant-adjustment-item-id, sku, quantity-purchased, promotion-id`。
- 手动下载路径：Seller Central「Payments > All Statements > Download Flat File V2」（来源：[卖家论坛帖](https://sellercentral.amazon.com/seller-forums/discussions/t/6b82228c-034f-45d4-a4b1-859a6dd6f43d)，非官方文档）。
- 解析规则：
  - 第一行数据通常只有 settlement 汇总信息（total-amount 等）而没有 transaction-type（「推断」，「待真实数据验证」）。
  - 日期格式、`transaction-type` 和 `amount-type/amount-description` 的取值全集「待真实数据验证」；未知组合 → 生成 `UNKNOWN_FEE_TYPE` 异常，不丢数据。
  - 校验：`Σ amount == total-amount`（同一 settlement-id），不等 → `SETTLEMENT_UNBALANCED` 异常。
- 替代来源：Finances API v2024-06-19 `listTransactions`（来源是 [GitHub issue 回复](https://github.com/amzn/selling-partner-api-models/issues/5285)，不是官方文档，「未核实」），v1.0 再评估。

### 5.2 Shopify Payments 打款 CSV — 官方帮助已核实基础列
- 来源：[Shopify 帮助中心：查看打款详情](https://help.shopify.com/en/manual/payments/shopify-payments/payouts/view-details)。后台 Finance > Payouts 可导出单次打款、待处理交易、或按日期导出全部交易，CSV 通过邮件发送。
- 官方列出的列：`Transaction Date`（带时区）、`Type`、`Order`、`Card Brand`、`Card Source`、`Payout Status`、`Payout Date`、`Available On`、`Amount`、`Fee`、`Net`。
- 第三方资料（[storepaperwork 指南](https://storepaperwork.com/guides/shopify-payments-transactions-export-columns-explained/)，非官方）还列了 `Checkout, Payment Method Name, Presentment Amount, Presentment Currency, Currency`，并称 2026-01-08 新增了 `Payout ID` 列、`Net = Amount − Fee` → 全部「待真实数据验证」。

## 6. 对账与利润规则

### 6.1 对账（人话）
1. 先查结算单自己是不是平的：一张结算单所有行加起来要等于它的总额。
2. 再把结算单里「订单类」的行，按「订单号 + SKU」找对应的订单；找到且数量一致 → 匹配成功。
3. 一个订单可能分几次结算（比如先收款后退款），所以按订单号把多次结算的行合在一起看。
4. 找不到、数量不对、金额不对、SKU 没映射、成本缺失……每种情况都生成一条异常，写清原因码和人话说明。
5. 本期订单在结算里找不到，可能下一期才结算 → 标「待下期」，不算错。

原因码（`issue.kind`）：`NOT_IN_ERP`（结算有、订单表无）、`NOT_IN_SETTLEMENT`（订单有、结算无，超过 N 天才报）、`QTY_MISMATCH`、`AMOUNT_MISMATCH`、`SKU_UNMAPPED`、`COST_MISSING`、`FX_MISSING`、`CURRENCY_MISMATCH`、`DUPLICATE_ROW`、`REFUND_WITHOUT_ORDER`、`UNKNOWN_FEE_TYPE`、`SETTLEMENT_UNBALANCED`、`PARSE_ERROR`。

匹配率定义（指标 2）：`已匹配的订单类结算行组数 ÷ 全部订单类结算行组数`；非订单类行（如月租、仓储费）不进分母，但单独列出。

### 6.2 对账伪代码
```text
function reconcile(store, period):
    for s in settlements(store, period):
        if sum(s.lines.amount) != s.total: add_issue(SETTLEMENT_UNBALANCED, s)
    groups = group settlement_lines where transaction_type in ORDER_TYPES by (order_id, normalize(sku))
    orders = index order_lines(store, period ± 60 days) by (platform_order_id, normalize(platform_sku))
    for key, lines in groups:
        if key.sku not in sku_map: add_issue(SKU_UNMAPPED, lines); continue
        o = orders.get(key)
        if o is None:
            if all(l.transaction_type is REFUND for l in lines): add_issue(REFUND_WITHOUT_ORDER, lines)
            else: add_issue(NOT_IN_ERP, lines)
            continue
        if sum_qty(lines, type=ORDER) != o.qty: add_issue(QTY_MISMATCH, lines, o); continue
        principal = sum(l.amount for l in lines if fee_category(l) == "principal")
        if o.item_price is not None and principal != o.item_price: add_issue(AMOUNT_MISMATCH, lines, o, diff)
        else: save_match(lines, o, rule="order_id+sku")
    for o in orders not matched and o.order_date < period_end - GRACE_DAYS:
        add_issue(NOT_IN_SETTLEMENT, o)
    assert every unmatched group has exactly ≥1 open issue      # 指标 2 的“100% 有原因”
```

### 6.3 SKU 利润（人话）
利润 = 销售收入 + 促销（负数） + 平台费用（负数：佣金、FBA 配送费等） + 退款（负数，含退回的费用） − 商品成本（数量 × 订单日期当时的采购单价） − 头程（数量 × 头程单价） − 广告费（v0.5 起，导入了才算，没导入就在报表上写「未含广告」）。
- 全部在结算币种下算，最后按用户填的月汇率换成人民币；汇率缺失 → `FX_MISSING` 异常，不猜汇率。
- 只在最后显示时四舍五入到分；中间全程 Decimal。
- 指标 3：maken 用 Excel 手算 20 个 SKU 的利润作为「标准答案」（golden file），自动测试要求**逐分相等**。

### 6.4 利润伪代码
```text
function sku_profit(store, period, sku):
    lines = matched_settlement_lines(store, period, sku) + unmatched_fee_lines_allocated(sku)
    revenue  = Σ amount where category in {principal, shipping_charge}
    promo    = Σ amount where category == promotion
    fees     = Σ amount where category in {commission, fba, other_fee}
    refunds  = Σ amount where transaction_type is REFUND
    qty_net  = Σ qty(order) − Σ qty(refund with restock)        # 退货是否回库「待真实数据验证」
    cost     = lookup sku_cost(sku, order_date) or raise COST_MISSING
    cogs     = qty_net × cost.unit_cost
    freight  = qty_net × cost.freight_per_unit
    ads      = Σ ads(sku, period) if ads_imported else None
    profit_ccy = revenue + promo + fees + refunds − cogs − freight − (ads or 0)
    profit_cny = profit_ccy × fx(period, ccy→CNY) or raise FX_MISSING
    return snapshot(..., inputs_hash = sha256(sorted input ids + calc_version))
```

### 6.5 智能体设计

**确定性代码做（不用 AI）**：文件解析、金额解析、标准化、匹配、利润、凭证生成、借贷平衡、审批校验、写账、审计。

**AI（LLM）只做这几件事**：
1. 未知表头 → 列映射**建议**（要用户确认）。
2. 未知费用类型 → 分类**建议**（要用户确认）。
3. 异常的人话解释草稿（例如「这单在 10 月结算里只有退款没有收款，可能是 9 月的订单」）。
4. 带引用的问答（「上个月哪个 SKU 最亏？为什么？」）。

**工具清单**（全部只读，`agent/tools.py`（历史表述；**已被 08 v4 第 4.4、10.4 节取代：只读动作直用，中风险可执行，改账最多起草/待审**））：

| 工具 | 输入 | 返回 |
|---|---|---|
| `list_settlements` | store?, period | 结算单列表 + 记录 id |
| `get_settlement_summary` | settlement_id | 总额、分类合计、行数 |
| `get_sku_profit` | sku?, store?, period | 利润快照（含每个组成部分）+ 记录 id |
| `top_skus` | period, by(profit/loss/fees), n | 排名 |
| `list_issues` | kind?, status?, period | 异常列表 |
| `explain_match` | order_id 或 settlement_line_id | 匹配规则、差额、原始行号 |
| `get_fee_breakdown` | sku/order_id, period | 费用明细 |
| `get_raw_row` | raw_row_id | 原始行内容（用于引用） |
| `search_rules_doc` | query | 本项目的规则文档段落（应用内关键词索引，三库一致，不上向量库） |【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】

**建议类工具**（只生成「待审批」项，不写账）：`propose_column_mapping`、`propose_fee_category`、`propose_issue_note`。

**护栏**：
- 智能体使用**只读数据库连接**（历史表述；**已被 08 v4 第 10.4 节取代：Agent 通过统一动作执行器按权限执行，禁止直接绕过服务层写库**）（SQLite `mode=ro` URI；MySQL 只授 SELECT 的账号；PostgreSQL 只读角色）；守卫测试在三库上都保证写语句失败。
- 输出类型固定为 `Answer{text, citations: list[Citation]}`，`Citation{record_type, record_id, source_file, row_no}`；没有引用的回答被校验器拒绝并重试一次，仍失败则回答「数据不足」。
- **数字校验**：回答里出现的每个金额，必须能在本轮工具返回值里找到（容差 0）；否则拒绝。
- 导入文件内容只当数据，不当指令（防提示词注入：`amount-description` 等文本字段在给模型时加上数据边界标记）。
- 每次提问最多 8 次工具调用、单次 token 上限可配置；所有 AI 调用记入审计日志和 `llm_call`（见 6.7；问题、工具调用、引用 id，不记 API key）。
- PydanticAI 的「人工审批工具调用」（[deferred tools 文档](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/#human-in-the-loop-tool-approval)）作为第二道保险；第一道保险是写账服务本身的审批检查。

**评测集（指标 5）**：`tests/eval/questions.yaml`，20 题，每题包含：问题、期望数值/结论、必须出现的引用记录 id。题型：利润排名 5、单 SKU 利润构成 4、异常原因 4、结算总额/费用 4、无答案题（应答「数据不足」）3。运行 `agent-erp eval --model <name>`（用 pydantic-evals），得分 = 数值对 + 引用含期望记录。CI 里用 PydanticAI 的测试模型跑「工具接线测试」（不花钱），真实模型评测每周手动跑一次并把结果存进 `docs/eval-results/`。

### 6.6 审计（业务审计 + 登录/权限审计）

人话：系统里每一次「改数」「批准」「导出」「登录」都留一条不能改的记录，写清楚谁、什么时候、改了什么、改前是什么、改后是什么、谁批准的。每条记录带上一条的哈希（哈希链），中间任何一条被改或被删，校验就会报错。

| 审计内容 | 记什么 | 什么时候记 | 哪周做 |
|---|---|---|---|
| 业务审计 `audit_log` | 谁（用户/智能体/系统 + 角色）、何时（UTC）、动作、对象、改前 `before_json`、改后 `after_json`、审批单与审批人、原因、IP、请求 id、是否自批 | 导入、对账结果、异常处理、成本/汇率/映射修改、凭证生成、提交/批准/驳回、写账导出、配置修改、审计导出本身 | W1 建表；W4 字段补全 |
| 登录/权限审计 `security_event` | 登录成功/失败（记尝试的用户名，不记密码）、登出、改密码、建/停用户、授予/收回角色、无权限被拒、会话过期、API token 创建/吊销 | 每次发生即写 | W5 |
| AI 调用 | 见 6.7；业务审计里只记「谁在何时问了哪个问题、引用了哪些记录」 | 每次问答 | W7 |

**防篡改与保留**
- 同一事务：业务修改和审计记录一起提交或一起回滚，不会出现「改了但没记」。
- 哈希链：`hash = sha256(prev_hash + 规范化 JSON)`；并发写入时锁 `audit_head` 一行（`SELECT … FOR UPDATE`，写在 dialects.py）保证链不分叉；`agent-erp audit verify` 可随时校验。
- 数据库权限：MySQL/PostgreSQL 上应用账号对审计表只有 INSERT/SELECT，UPDATE/DELETE 会被数据库拒绝（`scripts/sql/grant_mysql.sql`、`grant_pg.sql`）；SQLite 无此能力，只靠哈希链发现篡改。【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】
- 导出：auditor 或 admin 可按时间段导出 CSV + JSONL + `manifest.json`（首尾哈希、行数、文件 sha256）的 zip；`agent-erp audit verify-export` 可离线校验；导出动作本身也记审计。
- 保留：业务审计默认永不自动删除；登录日志和 LLM 原文内容默认保留 180 天（「估算」，可配置）；清理前先写 `audit_checkpoint` 记录被清理部分的末尾哈希，剩余链仍可校验。会计档案的法定保管期限「未核实」，发布前请 maken 向会计确认。
- 查看：网页「审计」页按人/时间/对象筛选，点开看改前/改后对比；只有 auditor/admin 可见全部。

### 6.7 LLM 监控

人话：每问 AI 一次，系统记一行「调用记录」：用了哪个模型、哪版提示词、花了多少 token 和钱、等了多久、调了哪些工具、引用了哪些记录、有没有出错。网页上有监控页，超预算会告警，换模型或改提示词后自动跑评测防止变差。默认不需要任何额外服务。

| 每次调用记录 | 来源 | 说明 |
|---|---|---|
| 模型、供应商 | OTel 属性 `gen_ai.request.model` / `gen_ai.response.model` / `gen_ai.provider.name` | PydanticAI 埋点自动产生 |
| token | `gen_ai.usage.input_tokens` / `output_tokens`；指标 `gen_ai.client.token.usage` | 同上 |
| 费用 | token × `config/model_prices.yaml` 单价 | 单价由用户填写，本项目**不内置任何价格**；没填则只显示 token |
| 耗时、错误 | span 开始/结束时间、`error.type`、状态 | 拒答（无引用）记为 refused |
| 工具调用 | 工具 span（名字、参数、返回的记录 id） | 写 `llm_tool_call`，参数先脱敏 |
| 引用 | 智能体输出结构里的 citations | 自己写入 `llm_call.citations_json` |
| 提示词版本 | `prompts/*.md` 文件 sha256 前 12 位 | 写 `prompt_version`；对应 OTel `gen_ai.prompt.name` |
| 用户、问题 id | 当前登录用户 | 和业务审计关联 |

**工具选择**

| 方案 | 用法 | 结论 |
|---|---|---|
| 内置：PydanticAI `Agent.instrument_all()` + 自写 `DbSpanExporter` 写自己的表（[PydanticAI 埋点文档](https://pydantic.dev/docs/ai/integrations/logfire/)；支持任何 OTLP 后端） | 零额外服务，数据留在本地数据库 | **默认**（v0.5 W7–W8） |

| Logfire（[说明](https://pydantic.dev/docs/ai/integrations/logfire/)） | 商业托管；自托管仅企业版 | 不作默认（卖家财务数据不出境） |
| OTel GenAI 语义约定（[仓库](https://github.com/open-telemetry/semantic-conventions-genai)） | 字段命名对齐它 | 状态仍是 Development（非 Stable），属性名可能变；在 db_exporter 里做一层映射 |

- **监控页**（W8）：按天/模型/用户看调用次数、token、费用、P50/P95 耗时、错误率、拒答率；点进一次调用看工具链和引用。auditor/admin 看全部，其他人只看自己的。
- **预算告警**（W8）：按月设全局或每人上限（金额或 token）；到 80% 网页提示 + `alert` 记录；到 100% warn 模式继续但告警，hard 模式拒绝新提问；第 3 月加推飞书。
- **评测回归**（W9）：换模型或改 `prompts/` 时跑 20 题，结果写 `eval_run`；比 baseline 少答对 1 题及以上或出现任何数字错误即判失败并告警；CI 用测试模型不花钱，真实模型手动触发（workflow_dispatch）。

- 提示词和问答原文保留 180 天（「估算」，可配置），统计数字永久保留。

**内置兜底（不装 Langfuse 时就靠这几张表）**：`llm_call`、`llm_tool_call`、`prompt_version`、`llm_budget`、`alert`、`eval_run`（字段见第 4 节）。

### 7.2 编码规范（写进 AGENTS.md）
- Python ≥3.12，开发用 3.14；`ruff format` + `ruff check`；`mypy --strict` 覆盖 `core recon profit vouchers approval ledger audit`。
- **金额禁止 float**：只能用 `core.money.Money`/`Decimal`；有测试扫描源码中对金额字段的 `float(` 用法。
- 所有时间带时区；存 UTC。
- 业务逻辑写成纯函数，数据库读写放 `db/repo`；每个规则有单元测试。
- **只有 `ledger/write_service.py` 可以 import `ledger/targets/*`**，用 `tests/guard/test_imports.py`（AST 扫描）强制。
- 新功能必须同时提交：代码 + 测试 + 文档（docs/ 或 README）+ CHANGELOG 一行。
- 提交信息用 Conventional Commits（`feat: / fix: / docs: / test:`）；一个 PR 只做一件事；PR 描述里写「如何验收」。
- 不提交任何真实卖家数据、密钥；`.env.example` 给出变量名。

### 7.3 测试与 CI



## 10. 风险与待解决问题

| 风险/问题 | 影响 | 应对 |
|---|---|---|
| 没有领星/赛狐真实导出样本 | 列映射全靠猜，指标 2 在真实数据上可能不达标 | W1 前拿到至少各 1 份；全部做成 YAML 映射；AI 只给映射建议 |
| 领星 API 需要卖家**主账号（超级管理员）**申请 AppID 并配 IP 白名单 | 个人开发者拿不到，API 连接器只能等试用卖家授权 | v0.x 只做文件导入；v1.0 视授权情况 |
| 赛狐开放平台文档需密码 | 无法评估 API | 只做文件导入；向赛狐客服申请文档（maken 自己联系） |
| SP-API 需提交开发者资料并通过审核，审核问题需 5 天内回复 | 时间不可控；审核时长 1–2 周的说法「未核实」 | 第 4 月才依赖它；文件导入始终可用 |
| Amazon 结算文件细节（首行汇总、日期格式、费用类型全集） | 解析失败或分类错 | 未知类型进异常；用真实文件补 fee_map.yaml |
| Shopify 新增列（Payout ID 等）只见于第三方资料 | 依赖它会出错 | 按表头名读、列可选 |
| 金蝶各产品线（云星空/精斗云/KIS）模板不同 | 引入失败 | 表头可配置；先支持 maken 手上的版本 |
| ERPNext 为 GPL-3.0 | 许可证风险 | 只走 REST，不复制代码，插件单独包（「推断」，上线前确认） |
| LLM 编造数字 | 财务信任崩塌 | 金额只由代码计算；数字校验器；无引用即拒答 |
| 一人兼职、春节 | 进度滑 | 每周只交付一个可验收块；第 3 月按半负荷排 |
| 用户数据隐私 | 卖家不敢试用 | 默认本地运行、数据不出电脑；模型调用只发聚合结果和必要行 |
| 三库方言差异（upsert、锁、日期函数、大小写/排序规则、VARCHAR 长度） | 某库上行为不一致、迁移失败 | 差异只写在 dialects.py；CI 三库全跑；禁止原生 SQL |【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】
| SQLite 没有精确小数、没有账号权限 | 金额精度或审计表防篡改弱于 MySQL/PG | Money4 在 SQLite 存整数万分位；哈希链；文档写明「团队用 MySQL 或 PostgreSQL」 |【历史验收口径；现行正式目标为 MySQL 8.4，SQLite 仅演示，PostgreSQL 仅备选】
| Langfuse 自托管要 4 个服务 | 卖家机器跑不动、安装指标受影响 | 只做可选 profile；默认内置表；可延到第 3 月 |
| OTel GenAI 约定仍是 Development | 属性名将来可能变 | 锁定 pydantic-ai 版本；db_exporter 做映射层 + 测试 |
| LLM 日志泄露买家信息 | 隐私风险 | 导入时不给模型；存脱敏文本；外发不带内容；脱敏测试 |
| 多用户 = 更大攻击面（弱密码、CSRF、越权） | 数据被改或泄露 | 默认只监听 127.0.0.1；argon2、CSRF、登录锁定；权限矩阵测试；对外必须 HTTPS |
| 工作量增加（W1/W5/W7–W9） | v0.5 可能延期（「估算」） | Langfuse profile 和飞书告警可延到第 3 月；字段级权限不做 |

**待 maken 决定的开放问题**：① 仓库/包名（暂定 agent-erp）；② 默认模型供应商（DeepSeek / 通义 / 其他）；③ 金蝶具体产品线；④ 退货回库是否计入数量（影响利润口径）；⑤ 广告费从哪里导入（领星报表还是 Amazon 广告报表）；⑥ 团队部署文档首推 MySQL 还是 PostgreSQL（两者都一等支持）（历史待拍板；**已被 08 v4 第 11.3 节取代：正式环境以 MySQL 8.4 LTS 为主**）；⑦ 是否允许「单人模式」自己批准自己提交的单据（历史待拍板；**已被 08 v4 第 12.1、12.3 节取代：取消单人模式**）（会被标记 self_approved；原文保留）；⑧ 新增验收项 A–F 是否纳入指标。
