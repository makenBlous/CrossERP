# CrossERP 整体设计总览

- 文档日期：2026-11-09（Asia/Shanghai）
- 文档性质：设计稿，不含应用代码
- 写作原则：沿用已有实施方案和红线；新增内容凡未在现有文档或官方来源中核实的，标为「未核实」「推断」或「估算」

本文是前端页面、后端模块、智能体接入和数据模型四份设计的入口。目标是：在不推翻现有对账、利润、审批、审计和「AI 不算钱」规则的前提下，把后续 ERP、CRM、智能体要用到的页面和功能模块一次性规划清楚，方便以后按模块扩展。

---

## 1. 一句话说明

CrossERP 继续做跨境出口电商卖家用的经营系统：先把现有「导入报表 → 对账和利润 → 异常处理 → 人批准后才出凭证」做成更好看、更好用的网页；同时把商品、订单、库存、采购、物流、广告、客户关系、智能体中心的页面和后台模块预留出来。智能体运行预期交给单独部署的 DeerFlow 2.0，CrossERP 负责业务数据、权限、审批、审计和智能体相关档案。

原实施方案（`docs/plan/实施方案.md`）把 v1.0 明确限定为「对账 + 利润 + 审批记账 + 只读问答」，并写明「库存/采购/生产等完整 ERP 模块」不在 v1.0。本次按 maken 的新要求把后续 ERP + CRM + 智能体页面和模块全部设计出来，**实施仍分阶段**，不把后期模块提前当成当前必须交付的功能。

---

## 2. 必须遵守的红线

这些决定已经写在实施方案和 ADR 里，本次设计全部保留：

1. **AI 不算钱**（ADR 0002）：对账、利润、凭证金额、借贷平衡全部由确定性代码和精确小数计算。AI 只做解释、建议和带出处的问答。
2. **不批准不写账**（ADR 0001）：对外写账和凭证导出只能走 `ledger.write_service`，必须先有人批准。
3. **合并后的表结构只追加**：可以加表、加列，不能删列、不能改已有列含义来迁就新功能。
4. **模型密钥不进仓库**：只放在使用者本机环境变量或本地配置（现有约定是 `CROSSERP_API_KEY` 等，见 `docs/agent.md`）。
5. **能改数、能批准、能登录、能问 AI 的动作都要记账**：业务审计和安全日志是哈希链，只追加（ADR 0003）。
6. **v1.0 完整成品之前不对外发布**：不打 tag、不上 PyPI、不发 GitHub Release。推送 main 可以，但发布策略仍由 maken 决定。
7. **开发直接在 main 提交**，不为每个任务建分支。
8. **凭证分录方向采用方案 A**，科目编码放在 `accounts.yaml`，默认值标注「待会计核实」。
9. **B/S 架构**：程序跑在一台电脑或服务器上，大家用浏览器登录。不做桌面客户端，不做多租户 SaaS（原计划 v1.0 明确不做）。

## 4. 这次设计要补上的缺口

maken 原话大意：先做前端重构和设计，把后续 ERP、CRM、智能体要用的页面全部设计出来，组件用本机 Vuexy；后端按功能模型把架构和模块设计完整，方便以后扩展；预留智能体的数据增删改查和接入，预期用 DeerFlow 2.0 快速介入。

因此本次交付四件事：

1. **前端**：用本机查到的 Vuexy 组件，规划完整菜单和页面清单，并说明如何从现在的 Jinja 页面过渡到独立的 Vue 单页应用。
2. **后端**：把现有扁平包整理成「可插拔的模块化单体」，列出全部功能模块、边界、事件、接口约定和加新模块的步骤。
3. **智能体**：核实 DeerFlow 2.0 的存在与接入方式，设计 CrossERP 与它的分工，以及智能体相关档案的增删改查。
4. **数据模型**：在现有表之上追加（不是推翻）后期模块和智能体所需的表与字段。

同目录还有一份 GNU GPL v2 文本（`Licensing/GPL.txt`）。Vue 版本主要是 Vue/TypeScript/CSS/设计资源，不是 WordPress 主题里的 PHP；因此上述第 (2) 点（按从 Envato 购买的许可证授权）对前端源码更直接相关。maken 买的是 Regular 还是 Extended，「未核实」。

> 8. You can’t re-distribute the Item as stock, in a tool or template, or with source files. You can’t do this with an Item either on its own or bundled with other items, and even if you modify the Item. You can’t re-distribute or make available the Item as-is or with superficial modifications. These things are not allowed even if the re-distribution is for Free.
>
> For example: You can’t purchase an HTML template, convert it to a WordPress theme and sell or give it to more than one client. You can’t license an item and then make it available as-is on your website for your users to download.

同页第 2、3、7 条还写明：Regular License 允许用该商品做一个终端产品且该终端产品可免费分发；终端产品必须是经过技能和劳动的定制实现；若要出售终端产品则需要 Extended License。

Envato 许可证常见问答（https://codecanyon.net/licenses/faq）对「扩展许可能不能拿来再分发商品本身」的说明是：

> No. You can’t license items and then make them available to others 'as-is' (that is, as a stand-alone item or as stock), regardless of which license you purchase.

**本设计不做法律结论。** 需要 maken 自行判断或向 ThemeForest / PixInvent / 法律顾问确认后，在下面几个方向里选一个：

| 选项 | 含义 | 对公开仓库的影响 |
|---|---|---|
| A. 前端保持私有 | Vuexy 源码和基于它的页面只放在 maken 本机或私有仓库 | 公开的 `makenBlous/CrossERP` 继续只放后端和文档 |
| B. 公开仓库只放后端 | 与 A 类似，但把前后端分成两个仓库，前端永不公开 | 后端仍是 Apache-2.0 |
| C. 询问版权方后另议 | 若确认某种深度定制的终端产品可以公开，再单独写说明 | 在未确认前，不把 Vuexy 源码提交到公开仓库 |
| D. 换一套可开源的前端组件 | 例如 Vuetify 官方示例 + 自研布局，不使用 Vuexy 源码 | 公开仓库可以同时放前后端；工作量「估算」会明显增加 |

在 maken 做出选择之前，设计文档可以进公开仓库（本文不包含 Vuexy 源码），但实施前端时不应把 `vuexy-admin-v10.11.1` 复制进 `https://github.com/makenBlous/CrossERP`。

## 7. 后端结论（详见 `02-后端架构与模块.md`、`04-数据模型.md`）

继续采用**模块化单体**：还是一个 Python 进程、一套数据库，但每个业务域是一个插件式模块——自己有模型声明、接口、权限、菜单、迁移说明和事件。这样以后加「库存」「客户」不必改对账内核。

模块分为四层：

1. **平台层**：`platform`（模块注册、事件、菜单清单）、`core`、`db`、`identity`（现有 `auth`）、`audit`、`files`、`jobs`、`notify`。
2. **业务层**：`catalog`（商品）、`sales`（订单）、`inventory`（库存）、`procurement`（采购）、`logistics`（物流）、`finance`（导入/对账/利润/凭证/应收应付/汇率，内部保留现有 `recon`/`profit`/`issues`/`vouchers`）、`ads`（广告）、`crm`（客户关系）。
3. **集成层**：`connectors`（亚马逊/Shopify/领星/赛狐等）、`ledger`（唯一写账出口）。
4. **智能体层**：`agent`、`mcp_server`、`observability`。

展示层：现有 `web`（Jinja）暂时保留；新增 `api`（`/api/v1` 的 JSON 接口）供 Vue 页面调用。两边共用同一套服务和权限。

多租户立场与原计划一致：v1.0 仍是**一家公司、多个店铺**，不做 SaaS 多租户。以后如果要做公司隔离，用追加字段的方式加 `company_id`，不改现有主键含义。

## 9. DeerFlow 2.0 接入结论（详见 `03-智能体接入与DeerFlow.md`）

**2.0 已核实存在**，不是口头版本号：

- 仓库：https://github.com/bytedance/deer-flow
- 发行说明：https://github.com/bytedance/deer-flow/releases/tag/v2.0.0 （标签 `v2.0.0`，发布时间 2026-06-25T16:23:22Z）
- 官方说明：DeerFlow 2.0 是推倒重写，与 1.x 不共用代码；1.x 留在 `main-1.x` / `1.x` 分支。
- 许可证：MIT（https://raw.githubusercontent.com/bytedance/deer-flow/main/LICENSE）
- 官网与文档：https://deerflow.tech ，架构说明 https://github.com/bytedance/deer-flow/blob/main/docs/ARCHITECTURE.md ，MCP 说明 https://deerflow.tech/en/docs/harness/mcp
- 检索时该仓库还有更新的 `v2.2.0`（发布页 https://github.com/bytedance/deer-flow/releases）。实施时应锁定一个明确版本；具体选用 2.0.0 还是更新的 2.x，请 maken 决定。本文按「2.0 这条产品线」设计，不绑定尚未在本地跑通的某一个补丁号。

接入方式（设计）：

1. DeerFlow **单独部署**（官方推荐 Docker 或 `make dev`，浏览器默认访问 http://127.0.0.1:2026）。
2. CrossERP 继续作为业务系统，通过 **MCP 工具** 把「查利润、查异常、查订单、提交建议」等能力暴露给 DeerFlow；现有 `crosserp mcp serve` 已是这条路的雏形。
3. 智能体要改业务数据时，只能在 CrossERP 里生成「待审批」记录，不能直接写账。
4. 网页对话优先做在 CrossERP 的智能体中心（统一登录和审计）；DeerFlow 自带的 Next.js 工作台可作为高级运维入口，不是卖家日常必用界面。
5. 模型密钥仍留在本机：CrossERP 用现有环境变量，DeerFlow 用它自己的 `.env` / `config.yaml`，两份都不进仓库。
6. CrossERP 增加智能体定义、工具授权、会话、运行、任务、知识库、提示词、评测、费用等档案表，作为系统内可查询、可审计的副本或主档。

## 11. 需要 maken 拍板的事项

1. **Vuexy 源码放哪里**：见第 6 节选项 A/B/C/D。在未选择前，不把模板源码提交到公开 GitHub。
2. **前端起步包**：建议 TypeScript + starter-kit；若 maken 更熟 JavaScript，也可以用 JS 版 starter-kit。两者 `package.json` 中的 Vue / Vuetify / Vite 版本一致（实查均为 9.5.0 标记）。
3. **DeerFlow 版本**：使用发行版 `v2.0.0`，还是跟踪更新的 2.x（检索时看到 `v2.2.0`）。
4. **日常对话入口**：卖家只在 CrossERP 里对话（推荐），还是也要同时使用 DeerFlow 自带工作台。
5. **CRM 的客户到底是谁**：本设计按「分销商 / 批发客户 / 独立站买家 / 合作渠道」来规划，不把亚马逊平台终端消费者做成主客户档（那些数据通常拿不到完整联系方式）。若 maken 有不同重点，需要说明。
6. **后期模块的先后**：库存、采购、物流、广告、CRM 哪一块先做。本文只设计，不排序实施（「推断」库存和订单对利润的帮助更直接，但不代替 maken 的选择）。
7. **这些设计文档是否推送到 GitHub**：本次只在本地仓库写入并提交，不推送。公开仓库目前是 Apache-2.0，设计文档本身不含 Vuexy 源码，推送设计文档与许可证冲突较小；是否推送仍由 maken 决定。
