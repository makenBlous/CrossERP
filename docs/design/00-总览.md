# CrossERP 整体设计总览

- 文档日期：2026-11-09（Asia/Shanghai）
- 文档性质：设计稿，不含应用代码
- 写作原则：沿用已有实施方案和红线；新增内容凡未在现有文档或官方来源中核实的，标为「未核实」「推断」或「估算」

本文是前端页面、后端模块、智能体接入和数据模型四份设计的入口。目标是：在不推翻现有对账、利润、审批、审计和「AI 不算钱」规则的前提下，把后续 ERP、CRM、智能体要用到的页面和功能模块一次性规划清楚，方便以后按模块扩展。

## 1. 一句话说明

CrossERP 继续做跨境出口电商卖家用的经营系统：先把现有「导入报表 → 对账和利润 → 异常处理 → 人批准后才出凭证」做成更好看、更好用的网页；同时把商品、订单、库存、采购、物流、广告、客户关系、智能体中心的页面和后台模块预留出来。智能体运行预期交给单独部署的 DeerFlow 2.0 —— **【已被 08 v4 第 10.0、10.1 节取代】**，CrossERP 负责业务数据、权限、审批、审计和智能体相关档案。

原实施方案（`docs/plan/实施方案.md`）把 v1.0 明确限定为「对账 + 利润 + 审批记账 + 只读问答」，并写明「库存/采购/生产等完整 ERP 模块」不在 v1.0。本次按 maken 的新要求把后续 ERP + CRM + 智能体页面和模块全部设计出来，**实施仍分阶段**，不把后期模块提前当成当前必须交付的功能。

## 2. 必须遵守的红线

这些决定已经写在实施方案和 ADR 里，本次设计全部保留：

1. **AI 不算钱**（ADR 0002）：对账、利润、凭证金额、借贷平衡全部由确定性代码和精确小数计算。AI 只做解释、建议和带出处的问答。
2. **不批准不写账**（ADR 0001）：对外写账和凭证导出只能走 `ledger.write_service`，必须先有人批准。
3. **合并后的表结构只追加**：可以加表、加列，不能删列、不能改已有列含义来迁就新功能。
4. **模型密钥不进仓库**：只放在使用者本机环境变量或本地配置（现有约定是 `CROSSERP_API_KEY` 等，见 `docs/agent.md`）。
5. **能改数、能批准、能登录、能问 AI 的动作都要记账**：业务审计和安全日志是哈希链，只追加（ADR 0003）。
6. **v1.0 完整成品之前不对外发布**：不打 tag、不上 PyPI、不发 GitHub Release。推送 main 可以，但发布策略仍由 maken 决定。
7. **开发直接在 main 提交**，不为每个任务建分支。
8. **凭证分录方向采用方案 A**，科目编码放在 `accounts.yaml`，默认值标注「待会计核实」。
9. **B/S 架构**：程序跑在一台电脑或服务器上，大家用浏览器登录。不做桌面客户端，不做多租户 SaaS（原计划 v1.0 明确不做）。

## 7. 后端结论（详见 `02-后端架构与模块.md`、`04-数据模型.md`）

继续采用**模块化单体**：还是一个 Python 进程、一套数据库，但每个业务域是一个插件式模块——自己有模型声明、接口、权限、菜单、迁移说明和事件。这样以后加「库存」「客户」不必改对账内核。

模块分为四层：

1. **平台层**：`platform`（模块注册、事件、菜单清单）、`core`、`db`、`identity`（现有 `auth`）、`audit`、`files`、`jobs`、`notify`。
2. **业务层**：`catalog`（商品）、`sales`（订单）、`inventory`（库存）、`procurement`（采购）、`logistics`（物流）、`finance`（导入/对账/利润/凭证/应收应付/汇率，内部保留现有 `recon`/`profit`/`issues`/`vouchers`）、`ads`（广告）、`crm`（客户关系）。
3. **集成层**：`connectors`（亚马逊/Shopify/领星/赛狐等）、`ledger`（唯一写账出口）。
4. **智能体层**：`agent`、`mcp_server`、`observability`。

展示层：现有 `web`（Jinja）暂时保留；新增 `api`（`/api/v1` 的 JSON 接口）供 Vue 页面调用。两边共用同一套服务和权限。

多租户立场与原计划一致：v1.0 仍是**一家公司、多个店铺**，不做 SaaS 多租户。以后如果要做公司隔离，用追加字段的方式加 `company_id`，不改现有主键含义。

## 11. 需要 maken 拍板的事项

1. **Vuexy 源码放哪里**：见第 6 节选项 A/B/C/D。在未选择前，不把模板源码提交到公开 GitHub。
2. **前端起步包**：建议 TypeScript + starter-kit；若 maken 更熟 JavaScript，也可以用 JS 版 starter-kit。两者 `package.json` 中的 Vue / Vuetify / Vite 版本一致（实查均为 9.5.0 标记）。
3. **DeerFlow 版本**：使用发行版 `v2.0.0`，还是跟踪更新的 2.x（检索时看到 `v2.2.0`）。
4. **日常对话入口**：卖家只在 CrossERP 里对话（推荐），还是也要同时使用 DeerFlow 自带工作台。
5. **CRM 的客户到底是谁**：本设计按「分销商 / 批发客户 / 独立站买家 / 合作渠道」来规划，不把亚马逊平台终端消费者做成主客户档（那些数据通常拿不到完整联系方式）。若 maken 有不同重点，需要说明。

### 14.2 智能体怎么「深度结合但可控」

1. **两条腿走路**：每个流程都有完整的人工做法；AI 只是在上面「提醒、起草、解释、预测、查数、识别票据」。AI 起草的单据和人填的单据是同一张表、同一条审批流。
2. **自主等级 L0–L3**：关闭 / 只建议 / 起草等审批 / 低风险自动做（可撤销）。按模块 × 动作 × 角色 × 金额配置，取最低值。**白名单里的低风险动作（票据分类、提醒等）第一天就自动执行**，有每日上限、日志和撤销。**钱和账最高 L2**，任何配置都改不了。
3. **AI 总开关**：正常 / 降级 / 关闭三档；模型故障、评测不达标、预算超限会自动降级；关闭后所有业务照常可做。
4. **可信控制**：每条建议带证据和把握度；提交前过确定性规则检查；做单和审单分开；评测基线；采纳率统计；预算上限；数据范围；全部进日志。
5. **智能体有自己的身份**，永远「替当前登录的人干活」，权限**等于**这个人，绝不更多；管理员可选收窄。钱和账要人批、不能自批是「动作护栏」，不是削减权限。
6. **权限是一张表**：权限点目录（菜单/动作/字段 + 数据范围）、可自建/复制/继承的角色（拒绝优先）、一人多角色、用户例外；16 个按跨境卖家分工的角色模板（老板/总经理、运营主管、店铺运营、广告投放、产品开发/选品、采购、仓储/物流、客服/售后、会计、财务主管、出纳、人事行政、部门主管、普通员工、审计、只读/外部顾问）。
7. **工具和渠道可扩展**：AI 工具注册表（联网结果是不可信数据）；通知/IM 渠道插件（飞书、企业微信、钉钉、邮件、Webhook）。
8. **一本操作日志**：人、AI、系统的动作在同一条防篡改哈希链上，分三个视图；每条 AI 建议都能追到「问了什么 → 调了什么工具 → 读了什么数据 → 输出什么 → 谁批的 → 产生什么效果」。
