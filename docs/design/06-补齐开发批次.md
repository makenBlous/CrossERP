## 1. 必须遵守的规则（每一批都一样）

1. **复用优先**：先用项目已有的 `components/biz/*`（`ListPage`、`DetailPage`、`FormPage`、`FormDrawer`、`RecordDrawer`、`StatusChip`、`MoneyText`、`PermissionGate`、`ConfirmHost`、`AssistantDrawer`、`KpiCard` 等），再用 Vuexy full-version 里对应的页面/视图/组件（按 01 第 20 节「Vuexy 对照」），最后才允许新写；新写必须在审计表里写明原因。
2. **AI 区不造新界面**：只用现有 `AssistantDrawer` + `AgentCard`（`kind: 'suggestion'`）+ 页面顶部 `VAlert` 提示条 + 表单「AI 预填」标签（见 05 第 9 节）。
3. **人工路径完整**：每个流程在「AI 关闭」状态下都要能从头走到尾。
4. **红线**：金额只由代码算（`MoneyText` 只显示）；凭证/付款/薪资最高 L2；不能自批、做单不能审单；**AI 权限等于当前登录用户，绝不更多**（管理员可选收窄）；L3 只限白名单。
5. **工作方式**：每批一个**分离头指针的工作树**（detached worktree），**不建分支**；完成后在主工作区按批次合并到 main，直接在 main 提交。
6. **冲突热点**：`config/pages.ts`、`plugins/i18n`、`mocks/seed`、权限种子数据。每批只在自己的模块文件里新增，`pages.ts`、i18n、权限点种子只在文件末尾追加一个以批次命名的块。
7. **每一批结束都要单独派一次 Codex 做组件复用审计**（沿用 `/workspace/fe/codex_audit_prompt.txt` 的模板，审计范围改为本批目录），审计替换后重新跑检查，结果写进 `frontend/docs/component-reuse-audit.md`。这是 maken 定的核心原则。
8. **验收**：`pnpm run typecheck`、eslint、`pnpm run build` 全过；Playwright 用 4 个以上角色模板逐页打开无报错；本批流程用真实点击跑通；再把 AI 切到「关闭」重跑主要流程；截图存 `/workspace/crosserp-shots/补齐-<批次>/`。

## 1b. 借鉴 ERPNext / Odoo（2026-11-10 maken 追加）

**原则**：功能、业务流程和设计尽量借鉴 ERPNext 和 Odoo，它们的业务价值和设计都经过大量企业验证。我们只改「核心」：以数据为中心，智能体作为智能层叠加在上面（建议、起草、解释、预测），传统人工流程完整保留。界面仍然优先复用 Vuexy 组件，不照搬它们的界面。

**落实方式**
- 模块、单据类型、状态命名：在合理的地方对齐 ERPNext 模块/DocType 与 Odoo 应用/模型的通行叫法；中文显示名不变；现有 128 页的路由和状态值不改，新页面在路由元数据里标注 `erpnextRef` / `odooRef`。
- 权限：
  - ERPNext：按角色给每种单据类型（DocType）授权 read/write/create/submit/cancel/amend/print/email/import/export/report 等；字段按 Permission Level（0–9，默认 0）分组授权；User Permissions 按链接值把用户限定在特定记录上（如某个店铺/仓库/公司）。来源：ERPNext 官方文档「Role Based Permissions」。
  - Odoo：用户属于多个组（`res.groups`），`implied_ids` 让一个组带出其他组（官方称「便利的伪继承」）；`ir.model.access` 按模型授予增删改查且多组取并集；`ir.rule` 记录规则用 domain 限定数据范围，全局规则取交集、组规则取并集；字段可用 `groups` 属性限制可见。来源：Odoo 18 开发文档「Security in Odoo」。
  - 我们在此基础上保留自己的规则：显式拒绝优先、有效权限带来源说明、AI 权限 = 当前用户 ∩ 收窄、钱和账最高 L2、不能自批。
- 单据状态：新单据采用 ERPNext 式「docstatus（0 草稿 / 1 已提交 / 2 已取消）+ 业务状态」两层（「推断」：两层对审批和审计更清晰）。

**各批次参考对象**（已在 GitHub 仓库目录或官方文档中核对存在；功能细节以对方文档为准）

| 0 地基 | Frappe 的 Role Permission Manager、User Permission、Workflow、Notification | `base`（res.groups、ir.model.access、ir.rule）、`mail` |

### 批次 A：财务做深 + 费用报销（19 页）

页面：EX01–EX07、F23–F34。

**必须修的断点和问题**

- **断点 3：订单 → 凭证**。目前没有订单级凭证。按 `voucher_rule` 设计实现：管理员选择每个店铺按「逐单」「按结算单」或「按期汇总」生成收入/应收凭证草稿；金额只取已存的确定性字段；汇总凭证通过 `voucher_source_link` 能逐条点回订单或结算单。
- **利润凭证期间写死在 2026-10**：改为可选择期间（默认上一个已结束的月），按所选期间取利润快照生成凭证草稿。
- **种子凭证 vch-1 详情没有审计记录**：给种子数据补上「起草 → 提交 → 批准」的审计记录，详情页时间轴正常显示。

**要跑通的流程**

1. **报销（AI）**：员工在票据收件箱上传发票 → AI 识别并预填（L3 分类、L2 起草）→ 员工确认提交 → 主管批 → 财务批 → 凭证草稿 → 预算占用转实际。
2. **报销（人工）**：AI 关闭 → 员工手填同一张报销单 → 同样的审批和凭证；超标准时规则检查拦截。
3. **借款冲抵**：借款 → 审批 → 报销时冲抵，余额由代码更新。
4. **订单 → 凭证**：选一个店铺设为「按结算单」→ 生成凭证草稿 → 从凭证点回结算单和订单；改为「逐单」再生成一次，结果不同但借贷都平衡。
5. **利润凭证**：选 2026-09 和 2026-10 各生成一次，期间正确。
6. **成本结转**：已确认出库 → 结转预览（代码算）→「借主营业务成本、贷库存商品」草稿 → 审批 → 进总账。
7. **结账**：有未审批凭证时不允许结账；结账后该期不能再生成凭证。
8. **报表**：科目余额表平衡；利润表、资产负债表数字能追到总账明细。
9. **预算预警**：报销让预算到 80% → 消息中心出现提醒。

### 批次 B：供应链 + 业务链 + 集成 + 渠道（20 页）

页面：S09–S13、I12–I15、D05、INT01–INT05、W08、SYS19、SYS20、SYS25、SYS26。

**必须修的断点**

- **断点 1：销售订单没有客户/商机字段**。订单增加 `customer_id`、`opportunity_id`；订单详情显示客户和商机链接，客户详情、商机详情反向列出订单；「商机赢单 → 生成订单草稿」时自动带上。
- **断点 2：采购退货没有明细行和数量、不扣库存**。增加退货明细行（SKU、批次、仓库、数量）；确认退货时每行写一条负数库存流水，库存总览和流水页能看到；同时生成应付冲减。
- **断点 4：订单发货没关联物流运单**。自发货订单在发货时关联运单号；FBA 订单关联头程批次；订单详情显示物流链接，运单详情反向列出订单。

**要跑通的流程**

1. **端到端链**：在业务链追溯页（D05）输入一个订单号，看到「客户/商机 → 订单 → SKU → 采购 → 入库 → 头程 → 出库/发货 → 凭证」整条链，4 个断点全部显示为「通」。
2. **补货（AI / 人工）**：低于安全库存 → 补货建议（数量代码算）→ AI 起草采购单进「智能体建议」→ 批准；AI 关闭时手动勾选新建。
3. **询价比价 → 采购单**（带 `rfq_id`、`contract_id`）。
4. **采购退货**：退 5 件 → 库存减 5、流水一条、应付减少。
5. **批次效期、调拨、盘点差异审批**。
6. **领星/赛狐导入**：上传 → AI 建议列映射 → 人确认 → 导入。
7. **渠道与 IM 审批**：新增一个钉钉渠道（模拟）→ 测试发送；员工绑定飞书（模拟）；IM 审批卡片预览页：¥3,000 报销卡片可批准且审计渠道显示「飞书」；¥80,000 付款卡片只显示「去网页确认」；内容被改过的卡片提示「内容已变化」。

### 批次 C：协作 + 权限表界面 + 操作日志（21 页 + 扩展现有页）

页面：W05–W07、N01–N02、RP01–RP03、U05–U08、SYS14–SYS18、SYS21–SYS24；扩展现有 `/approvals`、`/audit`、`/admin/roles`、`/admin/permissions`、`/admin/users/:id`、`/admin/notifications`。

**要跑通的流程**

1. **统一审批**：报销、请假、采购、凭证、智能体建议在同一个「待我审批」里，按类型筛选；多级与额度（¥3,000 主管批完结束，¥8,000 转财务）。
2. **自建角色**：复制「店铺运营」为「欧洲站运营」→ 改数据范围为欧洲店铺 → 指派给一个用户 → 该用户菜单和数据随之变化。
3. **继承与拒绝优先**：「运营主管」继承「店铺运营」；对「运营主管」显式拒绝「导出订单」→ 有效权限查看页显示该项被拒绝及来源。
4. **用户级例外**：给某用户单独允许「查看采购成本」7 天 → 到期自动失效。
5. **权限矩阵**：批量勾选后保存前显示影响用户数；保存后权限变更记录出现，敏感权限需第二个管理员确认。
6. **职责分离**：AI 替张三起草的单，张三的「批准」按钮不可用，后台也拦截。
7. **字段权限与数据范围**：只读角色看不到成本；部门主管只看本部门。
8. **AI 追溯与敏感告警**：在 AI 操作日志点开一条建议看到完整链；修改角色权限触发告警。

### 批次 D：智能体可控中心 + 工具注册表 + 人事行政（26 页）

页面：G18–G26、HR01–HR12、AM01–AM05；扩展现有 `/agent/tools` 为工具注册表。

**要跑通的流程**

1. **自主等级**：白名单动作首次进入即为 L3（票据分类自动执行、可撤销、达到每日上限后降为 L1）；把「凭证起草」设为 L3 不被允许。
2. **AI 总开关**：降级 → 只读提示、L3 暂停；关闭 → AI 区全部隐藏，其他批次的主要流程照常可走。
3. **AI 权限等于用户**：切换为「普通员工」后问 AI 看不到别人的报销和任何薪资；管理员给某智能体收窄「禁止联网」后，该智能体调用联网工具被拒并记日志。
4. **工具注册表**：新增一个自定义 HTTP 工具（默认停用、只读）→ 配置密钥（页面只显示「已配置」）→ 设频率上限 → 启用 → 测试调用；登记一个 MCP 服务器 → 导入工具后默认停用；联网结果在回答中带网址，且不能直接触发起草动作。
5. **算薪**：维护一个城市的社保/公积金规则（标「待会计/HR 核实」）→ 录入专项附加扣除 → 发起算薪 → 按累计预扣法算出个税（假数据用固定样例核对）→ HR 复核 → 财务审批 → 凭证草稿 → 员工「我的工资条」只看到自己的。
6. **入离职、请假、资产**流程。
